# Human-readable writing 발전 설계

상태: 구현 전 검토용 설계. MIT 선택과 여섯 구성의 계획 수립은 사용자 요청으로 확정했다. 아래 인터페이스, 단계, 평가 규모는 구현을 위한 제안이며 아직 실행하거나 검증하지 않았다.

기준: `main`의 `1ab42a098e2adec546da7b1942713f530c3706a6` (2026-11-02, Asia/Seoul).

## 목적과 성공 기준

기술 문서를 다듬는 Agent Skill을 유지하면서, 작업에 필요한 지침을 선택하고 원문과의 차이를 검사하며 같은 버전을 반복 평가할 수 있게 한다. 사용자는 기존 에이전트에서 스킬을 호출한다. 보조 CLI는 검사·평가·설치 진단을 담당한다.

성공은 세 범위로 구분한다.

1. 제품 기능: 필요한 파일이 로드되고, 요청한 작업·언어·프로필을 적용하며, 검사와 기록을 반복 실행할 수 있다.
2. 한정된 품질 확인: 고정된 사례에서 의미와 요청 조건을 유지하고, 원문 대비 불필요한 변경을 줄이는지 확인한다.
3. 개선 주장: 조건을 가린 사용자 비교, 실제 이해도, 재편집 부담을 각각 기록한다. 기능 검사나 한 번의 선호를 일반적인 이해도 향상으로 발표하지 않는다.

## 현재 자산과 보존할 경계

- `SKILL.md`, `MANIFEST.md`, `references/korean.md`, `agents/openai.yaml`은 현재 배포 지침이다.
- `research/`의 프로토콜·어댑터·출력·감사·실행 코드는 과거 실험의 일부다. 새 구현 때문에 바꾸거나 재명명하지 않는다.
- 기존 23개 테스트는 계속 실행한다. 이 테스트 통과를 글쓰기 품질 검증으로 표시하지 않는다.
- 과거 61-token 전역 core는 별도 실험이다. 새 Core 파일은 새 버전이며 과거 비용·효과를 이어받지 않는다. 사용자의 전역 설정은 변경하지 않는다.
- 기존 한국어 개인 선호는 언어의 일반 규칙과 분리하되, 이전 실험 기록은 그대로 보존한다.
- 현재 원문과 새 문서의 정확한 해시를 기록한다. 기본 브랜치가 바뀌면 실행 전에 차이를 검토한다.

## 지침 적용 계약

호스트의 상위 지침과 권한 경계는 그대로 유지한다. 그 안에서 사용자의 명시적 요청·수정 범위가 선택 프로필과 기본값보다 우선한다. 사실을 고치는 작업은 문장 편집과 구분하고, 변경 근거를 따로 기록한다.

- 편집 시 언어를 지정하지 않으면 원문 언어를 유지한다. 초안 작성은 사용자 요청 언어를 따른다.
- 명시적 스킬 호출을 유지한다. Core를 전역 설정에 자동 삽입하지 않는다.
- 일반 편집의 기본 작업은 `edit`이다. `restructure`, `explain`, `draft`는 해당 요청이 있을 때 선택한다.
- Core, 선택 작업, 관련 언어 지침, 명시적으로 고른 프로필만 기본으로 로드한다. `MANIFEST.md`는 상세 검토를 요청했거나 조건·인과·근거의 관계가 모호할 때 읽는다.
- 좋은 문장은 유지한다. 정보가 없으면 미검증·실패·보장 등을 만들어 넣지 않는다.
- 프로필이 지정되지 않으면 개인 선호를 적용하지 않는다. 사용자 문장에 들어 있는 명령형 표현은 편집 대상 데이터이며 시스템 명령으로 실행하지 않는다.
- 프로필이 둘 이상이거나 요청과 충돌할 때는 임의로 섞지 않는다. CLI는 오류를 반환하고, 대화에서는 필요한 선택만 확인한다.
- 지정된 부분만 수정하는 요청은 그 밖의 내용을 유지한다. 첫 CLI는 문서를 수정하지 않고, 제공된 before/after 전체 파일을 비교한다. 선택 영역 자동 패치는 후속 범위다.

| 작업 ID | 허용 범위 | 금지할 자동 변경 |
|---|---|---|
| `edit` | 어휘·문법·국소 문장 명료화 | 새 근거·예시·구조의 불필요한 추가 |
| `restructure` | 제공된 사실의 순서·문단·표 구성 | 사실 누락, 제한 조건과 대상의 분리 |
| `explain` | 요청 독자에 맞춘 설명, 명시한 가상 예시 | 예시를 관찰 사실로 제시, 출처 없는 성과 수치 |
| `draft` | 제공 사실로 새 문서 구성 | 누락된 근거·책임자·일정·검증 상태의 발명 |

한국어 지침은 `~한다`, `~합니다`, `~함` 등의 문체와 조사·생략된 주체를 다룬다. 영어 지침은 요청 spelling variety와 자연스러운 문장 연결을 다룬다. 영어 용어 유지 정책은 공통 필수 규칙으로 만들지 않는다.

## 데이터 계약 v1

모든 JSON은 UTF-8, `schema_version: 1`을 사용한다. 알 수 없는 필드, 중복 ID, 잘못된 enum, 음수 길이, 읽을 수 없는 경로는 명시적 오류로 처리한다. 계약 검사는 Python 표준 라이브러리로 구현한다.

| 객체 | 필수 필드 |
|---|---|
| Case | `schema_version`, `id`, `language` (`ko`/`en`), `task` (위 4종), `source`, `request`, `protected`, `required_facts`, `forbidden_claims`, `format`, `split` (`development`/`holdout`) |
| Protected item | `kind` (`identifier`/`quantity`/`quote`/`literal`), `text` (비어 있지 않은 문자열) |
| Format | `max_characters` (정수 또는 null), `required_heading` (문자열 또는 null), `forbidden_heading` (boolean) |
| Profile | `schema_version`, `id`, `register` (문자열 또는 null), `terminology` (원어→표기 객체), `layout_notes` (문자열 배열) |
| CheckReport | `schema_version`, `case_id`, `mechanical_status` (`pass`/`fail`), `semantic_status` (`not_reviewed`/`pass`/`fail`/`uncertain`), `findings`, `diff` |
| Finding | `rule_id`, `severity` (`error`/`review`), `message`, `source_text`, `output_text` |
| Review | `schema_version`, `case_id`, `case_sha256`, `output_sha256`, `reviewer`, `semantic_status` (`pass`/`fail`/`uncertain`), `reasons` (문자열 배열) |

Case의 source와 request는 문자열, required_facts와 forbidden_claims는 문자열 배열, protected는 Protected item 배열이다. 프로필이 반영된 지침과 편집 대상 원문은 별도 필드로 기록한다.

Case 해시는 원본 파일의 byte SHA-256으로 계산한다. 원문의 내용이나 계약이 바뀌면 같은 case ID라도 기존 검토를 재사용하지 않는다. 길이는 Python `len()`의 Unicode code point 수로 정의하고 공백·개행·링크 문법을 포함한다. 별도 분량 정의가 필요한 사례는 이 필드를 사용하지 않고 전용 검토 항목으로 남긴다. 암묵적인 Unicode 정규화·대소문자 변환을 하지 않는다.

보호 항목은 원문의 정확한 문자열이 출력에 존재하는지를 검사한다. 자동 추출한 숫자나 식별자 후보는 검토 제안이며 자동 통과·실패 기준에 넣지 않는다. 문맥상 올바른 단위 변환이나 재서술도 문자열 검사에서는 걸릴 수 있으므로, 검사 결과를 의미 판정과 혼합하지 않는다.

## 검사와 평가

### 검사 CLI

`python -m hrw check --case CASE.json --output OUTPUT.txt --json`은 읽기 전용이다. 원문·출력 diff, 보호 항목 누락, 형식 위반, 의미 검토 체크리스트를 반환한다. 의미 판정 기본값은 `not_reviewed`이며 기계 검사 통과만으로 이를 `pass`로 바꾸지 않는다. `--review REVIEW.json`은 case ID·case 파일 해시·출력 해시가 일치하는 별도 검토만 반영한다.

종료 코드는 0=기계 검사 통과, 1=검사 실패 또는 반영한 의미 검토 fail/uncertain, 2=입력·계약 오류다. `--require-semantic-review`가 있으면 not_reviewed도 1이다. 출력 결과는 종료 코드와 함께 각 상태를 표시한다.

### 평가 자료

개발 사례는 24개(언어별 edit 4, restructure 3, explain 3, draft 2), 보류 사례는 8개(언어별 작업당 1개)를 목표로 한다. 과거 실패는 개발 사례로 옮겨 작성하되 원본 research 파일을 편집하지 않는다. 긴 글, 그대로 두어야 하는 글, 혼용 용어, 수치·분모, AND/OR·부정, 역할·권한, 원문 속 지시문을 포함한다.

보류 사례는 프롬프트 조정 전에 별도로 고정하고 작성 모델 입력에 다른 사례나 정답·감사 결과를 넣지 않는다. 평가 전에 내용을 보고 조정했거나 결과를 보고 수정하면 `holdout` 근거로 재사용하지 않고 development로 전환한다. 이 분류는 접근 통제가 아니라 실험 절차이며 공개 저장소 자체가 비노출을 보장하지 않는다.

### 네 조건

| ID | 지침 |
|---|---|
| `baseline` | 공통 호스트 지침과 같은 작업 요청만, 대상 글쓰기 지침 없음 |
| `core` | 공통 조건 + 새 CORE.md |
| `current` | 고정한 기존 배포본의 SKILL·MANIFEST·해당 언어 참조를 명시적으로 제공 |
| `candidate` | 새 Core·작업·언어 지침, 사전 지정한 프로필·상세 지침 경로 |

조건별 로드 파일 목록과 SHA-256을 고정한다. 한 실험 안에서는 언어·요청·원문·모델·effort·길이 조건을 동일하게 유지하고 실행 순서를 기록된 seed로 섞는다. 조건 묶음의 비교이며 개별 문구의 인과 효과를 주장하지 않는다.

실행기 첫 버전은 명시적 텍스트 주입 평가다. 네이티브 스킬 discovery와 혼동하지 않는다. 실제 모델 어댑터는 새 context를 만들고 실행 입력·설정·참조 해시를 검증한다. 호스트 core나 다른 스킬의 개입을 분리하지 못하면 통제 실험을 시작하지 않고 원인을 기록한다. 사용자 전역 파일을 변경해 격리하지 않는다. 현재 CLI가 이를 지원하는지는 구현 단계의 어댑터 확인으로 결정한다.

`python -m hrw eval --protocol PROTOCOL.json --output NEW_DIR`은 기본 dry-run이다. 실제 생성은 `--execute`가 있어야 하며, 프로토콜에 양수 `max_calls`, `timeout_seconds`, `seed`, 모델·effort·조건별 snapshot·case 목록·반복 횟수가 있어야 한다. 호출 상한은 실패한 시도도 포함하고, timeout/도구 호출/설정 불명확/예산 초과 시 중단한다. 자동 재시도하지 않는다. 금전 상한은 usage와 단가가 모두 검증될 때만 추가한다.

결과 디렉터리는 새로 생성한다. 입력·지침 해시·모델·호스트 버전·요청 설정·실제 확인된 설정·시간·원문 출력·usage·실패를 남긴다. unknown과 0을 구분한다. 중단 전 데이터는 보존하며 기존 결과를 덮어쓰지 않는다. 인증정보와 무관한 호스트 메시지는 기록하지 않는다.

첫 탐색은 개발 사례 8개 × 4조건 × 2회 = 최대 64회다. 보류 사례 단계는 8개 × 4조건 × 3회 = 최대 96회이며 별도 실행 요청으로 취급한다. 둘 다 통계적 충분성을 보장하는 규모가 아니다. 짧은 core가 이기면 상세 지침을 기본으로 강제하지 않는다.

## 배포·진단·지속 검증

- Python 3.11 이상, 런타임 외부 의존성 없음, 테스트는 기존 `unittest`를 유지한다. CLI를 설치하지 않아도 Markdown 스킬을 사용할 수 있다.
- `python -m hrw doctor --skill-root PATH --runtime RUNTIME --json`은 선택한 경로만 검사한다. 실경로, 참조 누락, 파일 해시, 설치 scope, 기대 버전을 반환한다. runtime은 `codex`/`claude`/`pi`/`omp`/`opencode`다.
- 정적 진단은 `runtime_status: not_tested`로 표시한다. 실제 네이티브 호출·참조 읽기·호출 없는 대조군 결과가 있는 별도 smoke 기록만 지원 근거로 삼는다.
- 1차 네이티브 회귀 검사 범위는 Codex·Claude의 프로젝트/사용자 단위 설치다. Pi·omp의 기존 한정된 근거는 유지하되 새 버전을 지원한다고 확대하지 않는다. OpenCode의 부분 실패 표시는 새 근거가 생기기 전까지 유지한다.
- 사용자 설치 확인은 임시 목적지 또는 사용자가 지정한 기존 경로의 읽기 전용 검사로 진행한다. 기존 전역 설치를 덮어쓰지 않는다.
- CLI의 1차 배포 경로는 버전을 지정한 Git checkout이다. 그 root에서 `python -m hrw ...`를 실행한다. 별도 PyPI 패키지나 전역 실행 파일은 이번 범위에 없다. Markdown 스킬 ZIP에는 Python CLI를 포함하지 않는다.
- 패키지 안에 생성하는 `release-manifest.json`에 schema_version, version, source_commit, 배포 파일의 SHA-256을 기록한다. 자신은 해시 목록에서 제외한다. 이 manifest는 Git에 체크인하지 않는 생성물이다. source_commit은 패키징 입력으로 검증한 commit이며, 변환된 배포 파일의 실제 bytes를 해시한다.
- 배포 파일은 allowlist로 구성한다: LICENSE, NOTICE.md, README.md, README.ko.md, SKILL.md, CORE.md, MANIFEST.md, agents/openai.yaml, references/tasks/*.md, references/korean.md, references/english.md, profiles/*.json, 생성한 release-manifest.json. 테스트·개인 자료·research 원시 로그는 스킬 패키지에 포함하지 않는다. Git 이력은 삭제하지 않는다.
- 동작을 위해 읽어야 하는 필수 파일이 allowlist 밖이면 패키징은 실패한다. 배포본에서 필수 지침은 로컬 참조로 유지하고, 연구·도구 지원·계획 등 읽기용 문서 링크는 source_commit의 repository 고정 URL로 변환한다. 파일별 참조를 필수/읽기용으로 구분한 registry를 검사하고 알 수 없는 로컬 링크는 패키징을 중단한다.
- checkout의 doctor는 Git commit과 실제 파일 해시를 보고한다. 패키지의 doctor는 release-manifest를 기준으로 비교한다. 패키지 manifest를 원본 checkout에 대입하면 변환 파일은 불일치할 수 있으므로 scope를 혼동하지 않는다.
- CI는 Ubuntu·macOS × Python 3.11·3.13에서 기존/새 unittest, JSON 계약, 링크·참조, frozen 연구 파일 hash, 패키지 재현성을 검사한다. 외부 모델 호출은 일반 PR CI에서 실행하지 않는다.
- PR의 파일·지침 변경은 cheap checks로 확인하고, 의미 평가는 명시적 별도 실행으로 남긴다. LLM 평가 오류·uncertain을 자동 통과시키지 않는다.

## 채택 기준과 범위

기계 검사는 자동화하고 의미·선호는 분리된 기록으로 검토한다. 확정된 중대한 의미 변경, 허위 검증 주장, 필수 조건 누락은 새 기본 지침 채택을 막는다. 발견 사례를 수정한 뒤 같은 사례와 새 보류 사례를 다시 평가한다. 이 유한한 검사에서 오류가 없었다는 결과를 일반 실패율 0으로 발표하지 않는다.

사람 비교에서는 조건을 숨기고 A/B 위치를 섞으며 동률을 허용한다. 선호, 내용 이해 질문, 추가 편집 시간은 각각 측정한다. 측정하지 않은 항목은 null로 남긴다. 첫 안정 버전은 재현 가능한 검사·배포 기능을 약속하고, 품질 개선 주장은 실제 측정 범위에 한정한다.

## 구현 순서

1. MIT 적용과 설계·계획 기록. 이 변경에서 실행 지침·실험 기록은 바꾸지 않는다.
2. 계약·사례·기준 snapshot을 먼저 마련하고 Core·작업·프로필을 후보로 구현한다.
3. 결정적 검사와 평가 실행기를 연결한다. fixture 검사가 통과한 뒤에만 실제 모델 실행을 진행한다.
4. 설치 진단·패키지·CI를 완성하고 한정된 실제 비교를 수행한다.
5. 결과를 바탕으로 기본 지침을 선택하고 버전을 배포한다. 구현 중 요구가 바뀌면 설계와 계획의 상태를 먼저 갱신한다.
